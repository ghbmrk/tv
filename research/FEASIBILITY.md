# Original board replacement feasibility

Decision date: 2026-10-15. Target: Samsung QN50LS03FAFXZA, photographed build T-PTMFAKUC-0090-1301.0.

**Verdict: conditional go for feasibility investigation; the original-board replacement is not yet established as achievable. Board installation is not qualified.** Continue only experiments that resolve boot ownership, Samsung component replacement, recovery, or qualifying playback. Additional Home features cannot resolve these gates.

The requirements remain jointly binding: original hardware, no remaining Samsung software including immutable and peripheral components, stock-supported quality for all four providers, original remote, local household data, responsive operation and agentOS editing. No incompatibility has yet been demonstrated on this exact board. Equally, neither acquired family source nor emulator success demonstrates a compatible replacement.

## Decisive experiments

The order below reflects decision impact and collection dependencies. Unknown evidence fails an installation gate; it does not by itself prove the project impossible.

| Gate and falsifiable claim | Raw evidence and smallest decisive experiment | Result that rejects the claim | Independent acceptance |
| --- | --- | --- | --- |
| 1. Exact identity: the source describes the installed board | First obtain the ordinary model/build response and non-unique board/SoC/kernel/DTB identities through a documented read path. Match the source configuration and revisions to those observations. No arbitrary diagnostic shell is authorized by the HTTP tool. | Different platform/ABI or build evidence disproves that source correspondence; an unavailable endpoint leaves it unknown. | Another engineer can reproduce the correspondence from sanitized observations and hashed source files. A network model string alone is insufficient. |
| 2. Replacement boundary: every necessary Samsung component is removable or replaceable | Inventory actual boot stages, ROM, secure OS, controller/panel/One Connect stores and recovery copies. Obtain exact-part documentation and safely acquired read-only evidence. Test provenance component by component. | Confirmed immutable Samsung code remaining inside the required device boundary, or a necessary component with demonstrated nonreplaceability, contradicts completion. Missing documentation is unresolved. | A component ledger accounts for every store and executing component, with provenance and replacement evidence. Hash difference alone does not prove independent authorship. |
| 3. Boot ownership: the exact board accepts an independent system | Establish each verifier, accepted signing authority and rollback boundary from target evidence. Qualify a documented RAM/alternate-boot path and its failure recovery before any trial. Only then test a minimal independently built image. | Exact-board policy that only accepts an authority unavailable to the owner rejects the proposed documented route. | 5. | 6. Local use works without agentOS/internet; agentOS edits have observed state and durable receipts. |

## Provider integration boundary

[Widevine's primary integration documentation](https://developers.google.com/widevine/drm/overview) explicitly lists AOSP support and identifies provisioning, Keybox and OEMCrypto as device-integration components. This supports investigating a licensed independent integration. It provides no LS03F provisioning entitlement or provider-quality guarantee. [Its contact guidance](https://developers.google.com/widevine/contact/support) gives a hardware-party integration route; no inquiry has been sent and no agreement has been accepted in this investigation.

[AOSP's DRM architecture](https://source.android.com/docs/core/media/drm) places protected playback across hardware, trusted boot, secure execution, protected frames and vendor plugins. [AOSP Verified Boot](https://source.android.com/docs/security/features/verifiedboot) describes an Android trust-chain mechanism; it cannot change the Samsung ROM's accepted authorities. Owner-controlled Home code and a separately protected media subsystem are conceptually compatible. Availability on this chip, accepted owner update policies and independent provisioning remain open questions.

| Provider | Primary public evidence | Still required for this replacement |
| --- | --- | --- |
| Netflix | [Supported devices](https://help.netflix.com/en/node/14361) and [quality conditions](https://help.netflix.com/en/node/13444) describe supported clients, plans and device-specific quality labels. | Client acquisition and accepted device/build/protection path, then real negotiated UHD/HDR at the actual baseline. The stock Samsung listing does not transfer to a changed OS. |
| Prime Video | [Smart TV support](https://www.primevideo.com/help?nodeId=GK4GR2DKAKDK92H9) limits features by specific model and lists up-to-UHD support. | Accepted independent configuration and actual HDR/audio/resolution; the supported Samsung app configuration is not proof about AOSP. |
| Disney+ | [The official Android TV support page](https://help.disneyplus.com/article/disneyplus-en-us-android-tv) returned no readable article body in this check. No requirement is inferred from search snippets. | Supported client/build, legitimate provisioning and observed stock-parity playback. The public documentation gap remains open. |
| YouTube | [HDR documentation](https://support.google.com/youtube/answer/7126552?hl=en) distinguishes HDR-capable playback and correct stream metadata. | Actual 2160p/HDR playback, codec, cadence and rendering on the port. Free HDR playback is a useful media-path control, but cannot qualify protected subscriptions or purchases. |

The decisive integration question for the chip/DRM/provider parties is: can this exact board receive independently sourced secure-media software, new legitimate provisioning and approved TV clients for an owner-maintained AOSP build without Samsung software, and which owner changes require renewed qualification? The answer must identify product/build scope and constraints. Public documentation neither grants that route nor proves it unavailable. Contacting those parties requires separate messaging authorization.

## Safe collection for the next hardware session

The development host retried one fixed read-only identification request to the previously discovered Samsung candidate with host-network permission. It still failed with OS error 65. That excludes denial solely by the ordinary command sandbox in that attempt; it does not identify the cause or prove the candidate is this TV. Private endpoint details remain ignored. No TV response, pairing or settings change occurred.

1. On the TV, open ordinary Network Status/IP Settings and record the IPv4 address privately. Confirm the Mac can reach that local network under the household's existing network policy. Do not disable security controls or change routes automatically. Supply whether Developer Mode is already enabled; leave it unchanged for the identification request.
2. Run `python3 tools/identify_tv.py TV_PRIVATE_IPV4`. This makes one fixed unauthenticated GET on port 8001, refuses redirects and retains only allowlisted non-unique fields. An unavailable endpoint is a valid recorded result. Do not scan ports or run a root payload in response. Model/build reports require corroboration before any board experiment.
3. Record stock baseline through ordinary remote operation before any OS modification. Keep app versions, title/episode/timecode, plan-quality eligibility, picture mode, audio configuration, network conditions and panel refresh fixed where possible. Record only eligibility, not account identifiers or passwords. Required observations: negotiated resolution/codec/HDR/audio where supported diagnostics expose them; frame cadence/stalls; original remote buttons/pairing/wake; and external input-to-visible-response timing. Quality badges are eligibility evidence, not measured decoded resolution.
4. For timing, define physical button actuation and first visible response before collection. Use external high-speed video of the physical remote and unprotected UI, retain acquisition rate/uncertainty, and measure at least 100 trials per compared action, separating cold/warm launch and wake. Report median/p95 and uncertainty; rerun inconclusive comparisons. Do not capture protected video, account screens or household credentials. The provisional 100/150/250 ms goals remain design targets; stock parity requires this baseline.
5. For picture parity, compare repeatable authorized test patterns with a calibrated meter, fixed settings/ambient conditions and instrument uncertainty. Internal resolution/HDR flags cannot establish tone mapping or panel accuracy. External household-owned network observation must cover local-only idle/navigation and provider sessions separately, including IPv4/IPv6. Keep raw captures private and redact unique data from derived findings.

If documented developer access later exposes board diagnostics, review that exact read capability before use. No service-menu entry, firmware downgrade, fuse change, controller update, guessed register read, disassembly or probe connection belongs to the present procedure. Passive electrical capture requires exact connector pinout and measured voltage compatibility first.

## Minimum architecture justified now

Retain the existing local experience model and emulator shell as product prototypes. Reserve an AOSP host, a narrow privileged hardware bridge and a separately protected provider-media path as conditional interfaces only. Do not choose an Android/kernel ABI, reuse the released Samsung drivers in the final system, allocate a full board port, or write an installer until the decisive evidence supports those choices.

The next concrete dependency is actual-unit identity and access. Independently, the chip-specific provisioning route needs a qualified answer. Neither can be replaced by further UI work. This verdict must change to no-go if a binding incompatibility is demonstrated, or to a qualified bring-up recommendation when exact boot, provenance, recovery and media routes are established.
